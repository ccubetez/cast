# PHASE 14 — Automation: разбор перед реализацией

Статус: **анализ, код не пишем**. По спеке (§17, Phase 14) автоматизация
включается только после отдельного разбора security, custody,
transaction authorization и legal. Это тот разбор.

Объём фичи: **Take Profit**, **Stop Loss**, **Timed Catch** (продать через T),
**Auto Pull** (автоматический PULL OUT при условии).

---

## 1. Фундаментальная проблема

CAST — non-custodial: ключи только в кошельке пользователя, каждая
транзакция подписывается вручную. Автопродажа по определению требует
исполнения транзакции **без подписи в момент срабатывания**. Вариантов три:

### A. Ключ на сервере — ❌ отпадает
Хранение приватного ключа/сида на сервере = custodial. Противоречит §8
спеки и здравому смыслу. Компрометация сервера = потеря всех средств.

### B. Предподписанные транзакции — ❌ не работает
Blockhash на Solana живёт ~60–90 секунд. Транзакция, подписанная сейчас,
невалидна через 2 минуты. TP/SL живут часами и днями. Также заранее
фиксировать slippage/output невозможно — рынок уйдёт. Непригодно.

### C. Delegated authority (SPL approve) — ⚠️ единственный реальный путь
Пользователь вызывает `approve` на token account: назначает delegate
(серверный ключ) с лимитом = точному amount позиции. Сервер-executor
позже строит Jupiter swap, где transfer authority — delegate, и
подписывает tx серверным ключом (он же fee payer). Подпись пользователя
не нужна — delegate уже авторизован.

Свойства:
- Ущерб при компрометации сервера ограничен суммой approve (позиция, а не весь кошелёк).
- Approve per-position, отзывается (`revoke`) после исполнения или отмены intent.
- SOL-обёртка и fee-оплата — на сервере (небольшие суммы, пополняемый fee wallet).
- **Но**: это полу-custody. Пока approve активен, сервер *технически может*
  вывести approve'd токены в обход правил. Доверие к серверу ≠ 0.

## 2. Security разбор

| Риск | Митигация |
|---|---|
| Server compromise → кража approve'd токенов | approve = точный amount одной позиции; revoke сразу после исполнения; мониторинг delegate-аккаунтов; alerts |
| Replay / double execution | intent id + статусная машина; исполнение строго один раз (DB constraint + tx dedupe) |
| Ложный триггер по манипулированной цене | не одна точка Jupiter price: подтверждение N тиков подряд (TWAP-lite), sanity vs StonkFun feed |
| Stop loss в иллюквиде не исполняется | честный UX: «stop loss не гарантирует цену исполнения»; max slippage; повторные попытки с эскалацией slippage до cap |
| Сервер упал → стоп не сработал | health monitoring; на странице intent — «executor alive: 12s ago»; ToS дисклеймер |
| MEV/sandwich на автопродажах | Jupiter + jito? отдельный вопрос; на малых суммах приемлемо |
| Фронт-ран триггеров | триггеры не публикуются on-chain (только intent в нашей БД) |

Fail-open vs fail-closed: executor по умолчанию **не исполняет**, если
данные о цене сомнительны (нет двух источников, RPC нестабилен).

## 3. Legal разбор

- **Custody-определения**: модель «пользователь пред-авторизовал точный
  объём, сервер исполняет без дискреции» — агентская, а не custodial.
  Но формально (FinCEN, MiCA) любая способность сервера двигать средства
  может трактоваться как control → серая зона. Для личного проекта с
  одним пользователем риск минимален; для публичного продукта — нужен
  юрист до запуска.
- **РФ-контекст**: крипта — имущество (259-ФЗ); автоматическая торговля
  от имени пользователя по его правилам — агентская схема. Налоговая
  база формируется в момент продажи — автоисполнение не меняет
  обязательств пользователя декларировать.
- **Terms of Service обязателен** до любого публичного доступа:
  - автоматические действия выполняются строго по правилам пользователя,
    без дискреции сервиса;
  - stop loss не гарантирует цену; исполнение может быть частичным или
    не состояться;
  - сервис не несёт ответственности за проскальзывание, сбои RPC,
    отказ источников данных;
  - не investment advice.
- **No derivatives/leverage** — в рамках спеки.

## 4. Предлагаемая модель (если решаемся)

### AutomationIntent
```
id, catchId, positionId (или ALL для catch-level),
type: TAKE_PROFIT | STOP_LOSS | TIMED,
triggerPct (напр. +50 / -40) | triggerAt,
maxSlippageBps,
delegateApproveTx, delegateAmount,
status: ACTIVE | TRIGGERED | EXECUTING | EXECUTED | FAILED | CANCELLED | EXPIRED,
createdAt, expiresAt (≤ 7 дней, обязателен),
executedTx, executedPriceSol, notes
```

### Flow
1. UI: на позиции/улове кнопка SET GUARD → intent form (тип, порог,
   slippage, срок).
2. Подписи: (а) сообщение-intent (auth), (б) одна tx `approve` delegate
   на точный amount. Оба intent показываются явно.
3. Executor (server, рядом со snapshot-тиком): каждые ~20–60с берёт
   ACTIVE intents → цены из price-service (уже есть!) → триггер?
   → swap tx с delegate authority → simulate → submit → revoke →
   запись результата.
4. Kill switch: глобальный + per-intent CANCEL (revoke on-chain).

### Ограничения безопасности (hardcoded)
- 1 intent на позицию; максимум N активных на кошелёк.
- expiresAt обязателен, ≤ 7 дней.
- Суммы — не больше текущего лимита CAST.
- Simulation-first обязательна; fail-closed.

## 6. Мои возражения (честно)

1. **Stop loss на small-caps почти бесполезен.** Токен может упасть -60%
   за две минуты; при slippage-cap продажа не пройдёт. Стоп даст ложное
   чувство защиты. Take profit — полезнее (продаём в ликвидность на росте).
2. **Delegate = полу-custody**, как ни назови. Противоречит духу §8.
   Единственный способ сделать честно — прозрачно показать в UI: «пока
   guard активен, сервер может продать эту позицию». Плюс точечные approve.
3. **Сложность executor'а** (цены, ретраи, частичные фейлы, gas) —
   это второй trading core. Не недооценивать.
4. **Legal для публичного продукта** — до запуска нужен юрист.

**Рекомендация**: начать с **14.1 (paper automation)** — вся UX-ценность
(«поставил сторожа, он сработал») без custody-рисков и legal-экспозиции.
По результатам paper-прогонов станет ясно, есть ли вообще смысл в 14.2+:
если paper-стопы покажут, что исполнение «не состоялось бы» в половине
случаев — реальная автоматизация бессмысленна на этом классе активов.

Решение — за пользователем.
